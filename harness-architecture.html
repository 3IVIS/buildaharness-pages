BUILD A HARNESS · SYSTEM ANATOMY

Inside the harness.

Every turn walks the same eleven layers, in the same order, whether it's the reference Personal Assistant or a flow drawn on the canvas. This is that loop — World Model through Reviewer Pass — read straight out of adapter/harness/. Click any layer below to open what's actually running inside it.

11control layers walked every non-trivial turn
9independent verification checks before a draft is trusted
6named recovery strategies, fixed escalating order
12diagnostic health dimensions feeding Control State
THE LOOP

Eleven layers, one turn.

The pipeline below runs top to bottom on every turn that isn't a trivial one-shot lookup. Five of the eleven — Diagnostics, Control State, Verification, Recovery, and Reviewer Pass — decompose into their own sub-checks, tiers, or named strategies; open those for the exact breakdown. The other six are simpler by design, so their panel is just the files and the one thing worth knowing about each.

1
Layer 1 World Model Fresh, typed beliefs formed for this turn, each stamped with a generation_id. + detail− close
Files: world_model.py · world_model_ops.py · staleness.py

Every belief carries the generation_id it was formed under. Downstream layers that read the world model assert their own step matches that id — read a belief formed under an older step and you get a StalenessError instead of a silently outdated answer. That guarantee is what Contradiction (Layer 4) and Control State (Layer 6) build on.

2
Layer 2 Evidence & Reasoning The evidence store backing the reply, weighted by how reliable each tool's results have actually been. + detail− close
Files: evidence.py · tool_reliability.py · tool_manifest.py

Not all evidence counts equally — a claim backed by a tool with a poor track record this session is weighted down rather than trusted at face value. The tool manifest is also the allowlist gate: an fn_ref not on it never reaches codegen or exec().

3
Layer 3 Hypothesis Candidate readings of an ambiguous message, generated and scored before a reply is drafted. + detail− close
Files: hypothesis.py

The harness doesn't commit to the first plausible reading of a request — it scores competing hypotheses against the evidence store first. Reviewer Pass (Layer 11) later checks the delivered reply against hypothesis_compatibility, so a hypothesis picked here isn't the end of the story if it stops matching what actually got produced.

4
Layer 4 Contradiction Checks a new belief against ones already on record — "the build is passing" against a "failing" belief from three turns ago. + detail− close
Files: contradiction.py · belief_graph.py

Most contradictions just get logged and downgrade confidence. One severity — SYSTEM_BREAKING — short-circuits everything downstream: Control State's Tier 1 check (Layer 6) sees it and forces BLOCKED immediately, before any of the coverage or diagnostic math even runs.

5
Layer 5 Diagnostics Twelve health dimensions, each normalised to 0–1, computed from the turn so far and fed straight into Control State. +12 dimensions− close
Files: diagnostics.py

Each dimension is one of four types — ratio, composite, entropy, or match_confidence — and every value is run through normalise() then assert_normalised() before anything downstream is allowed to read it. Drop below 0.2 on any of these and Control State's Tier 2 check routes to a specific named recovery action.

belief_freshnesshow recently the beliefs behind the current answer were formed → belief_refresh
belief_consistencyagreement across beliefs on record → consistency_repair
belief_supportevidence backing beliefs currently in play → support_augment
symptom_coveragehow much of the reported problem space has been examined → coverage_expand
explanation_coveragehow much of the observed behaviour has a stated cause → explanation_expand
verification_strengthhow thoroughly the current output has actually been checked → verification_pass
verification_feasibilitywhether the checks that should run even can, given available tools → feasibility_check
progress_rateforward motion across the task graph → execution_retry
failure_recurrencewhether the same failure keeps resurfacing → failure_recovery
oscillation_scorewhether the run is flip-flopping between states → oscillation_stabilise
dep_graph_qualityintegrity of the task dependency graph → dep_graph_refresh
world_model_integrityoverall soundness of the current world model → consistency_repair
6
Layer 6 Control State Five-tier resolver → NORMAL / CAUTIOUS / BLOCKED — the sole control input for action selection. +5 tiers− close
Files: control_state.py

resolve_control_state() is the only function allowed to write a new control state (INV-06) — nothing downstream, including a Reviewer Pass re-entry, can set it directly. The five tiers run in strict order and the first one that fires wins:

Tier 1any SYSTEM_BREAKING contradiction on record → BLOCKED immediately, no further tiers evaluated
Tier 2any diagnostic dimension below 0.2 → BLOCKED, tagged with its recovery action; if the resulting block set forms a cycle, detect_deadlock() escalates to HUMAN_REQUIRED
Tier 3coverage dimensions between 0.2 and 0.4 → CAUTIOUS, exploration actions still allowed
Tier 4proportional caution elevation — blended with matched-failure-pattern confidence, tips to CAUTIOUS past a small threshold
Tier 5nothing above fired → NORMAL
7
Layer 7 Planning A task graph with six task states and dependency tracking, so parallel work doesn't collide. + detail− close
Files: task_graph.py · parallel_merge.py

Every task moves through PENDING → ACTIVE → VERIFYING → COMPLETE, with FAILED and BLOCKED as the off-ramps Recovery (Layer 10) hooks into. A task also carries its own LOW / MEDIUM / HIGH risk rating, read by Execution's review gate before anything under it runs.

8
Layer 8 Execution Value-of-information estimated, a five-dimension review gate runs, then — and only then — the action fires. +5 review dims− close
Files: execution.py · voi.py · risk.py · review_gate.py

A proposed change is checked against five independent dimensions before it's allowed to run — two consecutive failures on any one of them trips an escalation, not a silent retry:

task_alignmentdoes the change match the task it's supposedly for
world_model_consistencydoes it agree with current beliefs
output_contract_precheckwill the shape of the output satisfy the contract before it's even produced
code_qualitybaseline quality bar on generated code/output
hypothesis_compatibilitydoes it still match the hypothesis Layer 3 scored highest
9
Layer 9 Verification Nine independent checks the draft has to clear before it's trusted — not passed on the model's word. +9 checks− close
Files: verification.py

Each layer maps to a specific backing tool. If that tool isn't available in the tool manifest for the current run, the layer is marked SKIPPED — never silently counted as a pass:

syntax→ linter
unit→ pytest
integration→ integration_runner
consistency→ consistency_checker
requirements→ requirements_checker
assumptions→ assumption_checker
goal_correctness→ goal_checker
evidence_sufficiency→ evidence_checker
output_contract_partial→ contract_checker
10
Layer 10 Recovery Six named strategies in a fixed, escalating order — a rollback-and-replan path instead of the run crashing out. +6 strategies− close
Files: recovery.py · replanning.py · memory.py

An experience-store-driven softmax can bias which strategy is tried first, but always falls back to this fixed order when the store is unavailable (INV-10). A failure-mode pattern library gives advisory bias only — it never overrides a caller's own decision:

1 · DIRECT_EDITsmallest possible targeted fix, tried first
2 · TRACE_EXECtrace execution to pin down where it actually went wrong
3 · BROADER_SEARCHwiden the search for context or a working reference point
4 · REIMPLEMENTthrow out the current approach and rebuild it
5 · MINIMAL_FIXaccept a smaller, safer fix over the ideal one
6 · ESCALATEhand off to a human — last resort, not a fallback taken lightly
11
Layer 11 Reviewer Pass A three-lens final check before the response leaves the harness — and it can send the turn back through the loop. +3 lenses− close
Files: reviewer.py

The same output is read through three separate lenses before it's allowed out:

implementerdid the work actually do what it set out to do
reviewera second read for gaps, regressions, and contract misses
adversarialactively tries to break it, seeded by a causal-proximity filter; its findings are ephemeral by design (INV-09) — never persisted outside this pass

Findings here aren't cosmetic: a propagation drain reopens any COMPLETE task whose underlying belief just got invalidated, sending it back through the loop. That re-entry still can't write control_state directly (INV-06) — only Layer 6's resolver does that, on the next pass.

↺ Recovery and Reviewer Pass are the two re-entry points — a failed action or an invalidated belief sends the run back through Planning or Verification, not out the door with a bad result.
Skipped on trivial turns

A single consolidated classification call up front (risk, triviality, decomposition, plan-abandonment, plan-template matching) flags a genuinely self-contained factual one-liner as trivial — that reply returns directly and none of the eleven layers above run. Everything else walks the full loop. See Personal Assistant for how this applies turn by turn in the reference chat agent.
